# 对话式学习计划闭环 V1 开发计划

## 1. 目标与边界

### 1.1 产品目标

用户只在现有对话页用一句自然语言表达计划需求，例如：

> 帮我制定三天复习《牙周病学》第三章的计划，每天 30 分钟，重点是炎症机制。

系统识别为现有 `study_plan` 意图后，生成有事实依据的计划草案。用户进入现有学习计划页逐项采纳；采纳后的计划项显示在日历中；点击“开始学习”后，学习链路必须按该计划项对应的教材、章节和知识点启动。

### 1.2 不在本期范围内

- 不新增计划页面、表单页或新的意图分类入口。
- 不改变 `MasterRouter` 的意图分类、`learning` / `direct_qa` / `literature` 调度规则。
- 不让“学习某教材第三章”这类直接学习请求进入计划链路。
- 不做长期自动排期、间隔重复、自动修改用户日历或自动判定计划完成。
- 不修改与本功能无关的 PPT、Direct QA、文献、知识图谱展示接口。

### 1.3 必须保持的现有行为

- 用户直接说“学习《牙周病学》第三章”时，现有分类结果应为 `learning`，直接启动学习路径。
- 用户明确说“制定/安排/规划计划”“今天学什么”时，现有分类结果为 `study_plan`。
- 计划页当前的月视图、单项采纳、全部采纳、编辑、完成、延期、删除等交互继续可用。
- 旧的 `POST /api/learning/plan/recommend` 调用（只带日期和数量）继续返回当前的通用推荐，保证旧调用兼容。

## 2. 已核实的现状

| 层级 | 现状 | 影响 |
|---|---|---|
| 对话路由 | `MasterRouter` 已把 `study_plan` 路由到 `_handle_study_plan`。 | 不需要改分类器。 |
| 计划生成 | `_handle_study_plan` 调用推荐服务时只传用户、当天日期；用户原始请求没有进入服务。 | 不同计划需求会落到相同的确定性推荐。 |
| 计划页 | 计划页从月视图 API 读取真实已采纳的计划项；“系统推荐”只请求日期和数量。 | 已采纳列表不是写死；推荐内容缺少本次对话上下文。 |
| 聊天计划卡片 | 已展示推荐项与“开始学习/打开学习计划”。 | 可以复用展示，不需要新页面。 |
| 开始推荐 | 前端仅传 `recommendation_id` 和日期；后端重新运行默认推荐再查找该 ID。 | 对话中的定制计划无法稳定恢复，可能错路由或过期。 |
| 计划项模型 | 已有 `task_type`、`learning_target`、`linked_course_*`、`kg_node_ids`。 | 缺少稳定的教材/章节范围对象。 |
| 学习启动 | `start_lesson()` 只接收主题文本；计划项的 `kg_node_ids` 未用于限制课程规划。 | 不能保证“第三章计划”进入第三章范围。 |
| 续学 | `continue_lesson` 计划项启动时直接推进下一节点。 | 当前节点为末节时会立即显示课程完成。 |

## 3. V1 用户旅程

```mermaid
flowchart LR
  A["对话页：一句话提出计划"] --> B["现有路由识别 study_plan"]
  B --> C["解析需求并校验知识图谱"]
  C --> D["生成临时计划草案"]
  D --> E["聊天页现有计划卡片"]
  E --> F["打开现有计划页，携带草案 ID"]
  F --> G["复用现有推荐区：编辑/采纳"]
  G --> H["写入正式日历计划项"]
  H --> I["计划页点击开始学习"]
  I --> J["按计划范围创建或恢复学习 session"]
```

### 3.1 路由判定

| 用户表达 | 既有意图 | V1 行为 |
|---|---|---|
| “学习《牙周病学》第三章” | `learning` | 原样直接进入学习路径。 |
| “复习第三章的炎症机制” | `learning` | 原样进入定向学习/复习路径。 |
| “帮我制定三天复习第三章的计划” | `study_plan` | 生成计划草案。 |
| “每天 30 分钟，安排本周牙周炎复习” | `study_plan` | 生成计划草案。 |
| “今天学什么” | `study_plan` | 维持通用推荐。 |

分类器只决定是否进入计划链路；计划内容解析发生在计划服务内部，不能反向修改路由分类。

### 3.2 对话修改与草案版本规则

用户在**采纳前和采纳后**都可以继续在现有对话框中提出调整，例如“时间太长了”“第二天只想复习炎症机制”“改成两天完成”。

统一规则如下：

1. 每次对话调整都基于当前上下文重新生成一份**新的计划草案**，并分配新的 `plan_draft_id`。
2. 新草案不会自动改写、删除或完成任何已采纳的正式计划项。
3. 用户采纳前，可反复在对话中调整草案，再打开计划页查看和采纳最新草案。
4. 用户采纳后，仍可在对话中生成新草案；用户必须在计划页显式采纳新草案，或手动编辑/删除旧计划项，才会改变日历中的正式计划。
5. 同一轮对话内可以将上一份草案作为再生成的输入上下文；过期草案只能提示重新生成，不能静默退回到通用默认推荐。

该规则让聊天具备持续协商能力，同时保证系统未经用户确认不修改日历中已经采纳的计划。

### 3.3 资料真实性规则

- LLM 只能从用户原话提取目标、天数、时长和复习重点，不能虚构教材、章节或知识点。
- 教材、章节、核心知识点必须通过现有 `GET /api/knowledge-graph/overview` 对应的知识图谱数据校验。
- 找到精确章节时，使用其 `chapter_key`、`document_id`、`book_title`、`core_ids`。
- 找到教材但章节不明确时，返回澄清信息或候选章节；不得伪造章节。
- 找不到教材或章节时，明确说明资料库中不存在该范围；可在用户同意后按主题生成通用计划。
- 用户明确写出的薄弱点可作为“用户指定”依据；只有有答题/掌握度证据时，才能标为“系统识别薄弱点”。

## 4. 架构与数据契约

### 4.1 计划草案与正式计划项分离

**计划草案**是对话刚生成、尚未采纳的临时结果；**正式计划项**是用户采纳后写入 `study_plan_items` 的日历任务。

这样可以避免聊天中一生成就修改用户日历，也避免当前“按 recommendation ID 重新生成默认推荐”的不稳定行为。

### 4.2 新增内部对象：`PlanDraft`

建议在学习计划服务中提供短期草案存储；其身份为随机、不透明的 `plan_draft_id`，并绑定 `user_id`、创建时间和过期时间。

```json
{
  "plan_draft_id": "draft_...",
  "user_id": "demo",
  "created_at": "...",
  "expires_at": "...",
  "source": "master_chat",
  "raw_request": "帮我制定三天复习《牙周病学》第三章的计划，每天30分钟",
  "request": {
    "intent": "review",
    "start_date": "2026-07-15",
    "days": 3,
    "daily_minutes": 30,
    "focus_text": "炎症机制"
  },
  "items": []
}
```

草案项必须含有可执行的 `learning_scope`：

```json
{
  "recommendation_id": "rec_...",
  "title": "复习《牙周病学》第三章：炎症机制",
  "task_type": "review_chapter",
  "learning_target": "炎症机制",
  "estimated_minutes": 30,
  "reason": "用户指定第三章复习；章节存在对应核心知识点。",
  "evidence_source": "user_request + knowledge_graph",
  "learning_scope": {
    "book_title": "牙周病学",
    "document_id": "...",
    "chapter_key": "chapter:...",
    "chapter_title": "第三章……",
    "kg_node_ids": ["..."]
  }
}
```

草案存储可以先采用当前进程内、带 TTL 的线程安全存储；服务重启或草案过期时，前端显示“这份计划已过期，请重新生成”。若后续需要跨进程部署，再迁移为数据库表，不应在 V1 预先扩大范围。

一次草案再生成可记录可选 `parent_plan_draft_id`。它只用于把“时间太长了”等后续意见关联到上一份草案的约束和任务范围；它不表示覆盖或更新父草案，更不表示更新正式计划项。

### 4.3 正式计划项的新增字段

在 `study_plan_items` 中新增一个可空 JSON 字段：

```text
learning_scope_json TEXT NOT NULL DEFAULT '{}'
```

对应 API 模型新增可选字段：

```json
"learning_scope": {
  "book_title": "...",
  "document_id": "...",
  "chapter_key": "...",
  "chapter_title": "...",
  "kg_node_ids": ["..."]
}
```

上下游规则：

| 写入方 | 写入内容 | 读取方 | 用途 |
|---|---|---|---|
| 草案采纳 | 已校验的 `learning_scope` | 月视图/计划页 | 展示教材和章节元信息。 |
| 草案采纳 | `task_type`、`learning_target`、`reason` | 计划页 | 展示任务类型与生成依据。 |
| 开始学习 Router | 正式计划项的 `learning_scope` | 学习启动服务 | 严格限定教材、章节、知识点范围。 |

旧计划项使用默认空对象，不影响现有创建、编辑和月视图读取。

### 4.4 接口调整

#### 保持不变

- 现有对话路由入口和请求形状。
- `POST /api/learning/plan/items` 的现有字段和语义。
- `GET /api/learning/plan/{user_id}/month` 的现有返回字段。
- 计划项“完成/延期/删除”接口。

#### 兼容性扩展

1. `POST /api/learning/plan/recommend`

保留原来的 `user_id`、`plan_date`、`max_items`，增加可选 `request_text` 和可选 `source`。只有 `request_text` 非空时才走“对话定制计划”分支；否则保持当前通用推荐。

2. 新增草案读取接口

```text
GET /api/learning/plan/drafts/{plan_draft_id}?user_id=...
```

只返回拥有该草案的用户的未过期草案。计划页用它加载聊天草案；不存在、越权或过期均返回明确错误。

3. `POST /api/learning/plan/items`

新增可选 `learning_scope`，计划页在采纳聊天草案时透传。老调用不传仍可工作。

4. Router 的推荐启动上下文

聊天中的“打开学习计划”只携带 `plan_draft_id` 到计划页；正式学习从计划页已采纳项的 `plan_item_id` 启动。V1 不再用未采纳的推荐 ID 直接启动课程，避免草案与正式计划脱节。

### 4.5 学习启动范围传递

当前 Router 对计划项只计算主题文本后调用 `start_lesson(user_id, topic)`；这无法让课程规划器知道章节范围。

将下列内部函数做**可选参数**扩展：

```python
start_lesson(user_id, topic, ..., learning_scope: dict | None = None)
plan_lesson(topic, user_profile=None, ..., learning_scope: dict | None = None)
```

规则：

- 普通学习请求不传 `learning_scope`，现有行为不变。
- 从正式计划项启动时，Router 读取并校验 `learning_scope` 后传入。
- 课程检索与大纲规划仅使用 scope 中对应章节、`document_id` 和 `kg_node_ids` 的资料。
- scope 无法匹配可用内容时返回“该计划关联的章节资料不可用”，不得悄悄退回全局模糊检索。

### 4.6 续学语义修复

`continue_lesson` 计划项的“开始学习”应恢复当前 session 的当前节点并生成该节点讲解；只有用户在学习界面明确点击“继续下一节”时，才调用现有 `continue_to_next_section`。

课程完成与计划项完成必须独立：

- `lesson_completed`：本次课程 session 已到末节；只在聊天中展示课程状态。
- `study_plan_items.status = completed`：用户在计划页明确点击完成；继续走现有完成接口。

## 5. 前端改动范围

### 5.1 聊天页

修改 `frontend/js/master-chat.js`：

- 保留现有计划卡片结构和计划意图展示。
- 当后端返回 `plan_draft_id` 时，将“打开学习计划”的链接改为带该 ID 的计划页地址。
- 不新增填写表单，不修改聊天的意图发起方式。
- 对草案项不提供绕过采纳的“开始学习”；用户先在计划页采纳，后从正式计划项开始学习。

### 5.2 计划页

修改 `frontend/js/learning-plan.js` 与现有页面模板：

- 页面启动时读取 URL 中的 `plan_draft_id`。
- 有草案 ID 时调用草案读取接口，并复用现有推荐面板渲染草案项。
- “采纳/全部采纳”复用现有创建计划项请求，补传 `learning_scope`、`task_type`、`learning_target` 和依据。
- 采纳成功后刷新现有月视图，因此正式计划项会出现在对应日期。
- 没有草案 ID 时，页面仍可使用原有“系统推荐”按钮。

计划页不新增一组新交互；只让当前推荐面板可以显示来自聊天的真实草案。

## 6. 开发顺序

### 阶段 0：建立回归基线

1. 运行现有计划、Router、聊天前端测试。
2. 记录当前“计划页通用推荐”“聊天计划推荐”“计划项开始学习”“继续课程”的请求与返回样例。
3. 不修改业务代码；确认工作树中用户已有的未提交文件不被本任务触碰。

验收：现有测试基线明确；没有文件被意外修改。

### 阶段 1：草案模型与定制计划生成（后端）

1. 在 `study_plan.py` 定义 `PlanDraft`、TTL 草案仓库和用户/过期校验。
2. 为 `recommend_study_plan` 增加可选 `request_text` 分支；空文本保持旧推荐逻辑。
3. 实现“用户需求提取 → 知识图谱校验 → 计划任务拆分”。
4. 在返回结果中加入 `plan_draft_id`、`learning_scope`、`evidence_source`。
5. 增加草案读取服务与 API。
6. 支持可选 `parent_plan_draft_id`：同一对话会话的后续意见生成独立新草案，不改写父草案。

验收：同一用户输入不同教材/章节/时长，草案范围与任务不同；后续修改产生新草案 ID 而非改写旧草案；无 `request_text` 时旧推荐保持不变。

### 阶段 2：对话链路最小接线

1. 保持现有 Router 分类逻辑不变。
2. 在 `_handle_study_plan` 中将已收到的原始 `message` 传给计划推荐服务。
3. 在聊天计划结果中把 `plan_draft_id` 写入“打开学习计划”链接。
4. 删除或禁用草案项绕过采纳直接开始学习的路径，避免临时推荐 ID 被重新计算。
5. 后续计划意见携带当前草案 ID 生成新草案；不得调用正式计划项更新接口。

验收：一句话计划请求在聊天中展示定制草案；打开计划页时 URL 带草案 ID；普通直接学习路由无变化。

### 阶段 3：计划页加载草案并采纳（前后端）

1. 为 `study_plan_items` 加 `learning_scope_json` migration、行映射、创建与更新支持。
2. 扩展请求模型和现有创建接口以接受可选 `learning_scope`。
3. 计划页读取草案 ID、加载草案、复用当前推荐面板显示。
4. 采纳时保存完整 scope，成功后刷新月视图。
5. 后续草案只有在用户打开并显式采纳后才改变日历；此前已采纳计划保持不变。

验收：聊天草案逐项或全部采纳后，在计划页的正确日期显示；刷新页面后计划项仍存在且保留范围。

### 阶段 4：正式计划项到学习路径的精确路由

1. Router 从 `plan_item_id` 查询正式计划项，优先读取 `learning_scope`。
2. 给 `start_lesson` 和 `plan_lesson` 加可选 `learning_scope`；普通调用完全兼容。
3. 将 scope 传入检索/规划层，实现按 `document_id`、章节与 `kg_node_ids` 限定资料。
4. 若 scope 失效，返回可读错误；不退回不受限主题学习。

验收：从“第三章”正式计划项开始时，课程的 source trace、学习大纲和首节知识点均来自该章节范围。

### 阶段 5：续学与完成状态修复

1. 修改 `continue_lesson` 计划项启动逻辑为恢复当前节点。
2. 验证“开始学习”不调用计划完成接口。
3. 验证课程 session 完成只改变课程状态，计划项仍等待用户显式完成。

验收：当前节点为末节时，点击计划项不会立即把课程显示为完成；只有用户在计划页勾选后计划项才完成。

### 阶段 6：端到端回归与异常体验

1. 草案过期、越权、服务重启后的提示。
2. 找不到教材/章节、章节没有可用核心点、scope 失效的提示。
3. 旧系统推荐、旧手动计划、旧计划项启动的兼容性。
4. 计划页、聊天页、Router 与学习链路全链路验证。

## 7. 测试清单

### 过程变更记录：推荐服务草案分支的异常契约返工（2026-07-15）

- 原节点/假设：阶段 1 的推荐服务可在 `request_text` 非空时组合 KG、语义解析与草案；解析或范围失败只要不退回通用推荐即可。
- 失效证据：`_recommend_custom_draft` 在调用 `create_plan_draft_from_text` 后捕获宽泛 `Exception` 并重包为 `RuntimeError`，会丢失父草案不存在、越权、过期与 scope 校验的明确类型；这与“可区分失败、不能静默 fallback”的需求不一致。

### 手工验收脚本

1. 聊天输入“帮我制定三天复习《牙周病学》第三章的计划，每天 30 分钟”。
2. 确认聊天卡片的任务、依据和章节与输入一致。
3. 打开计划页，确认看到同一份草案而非默认推荐。
4. 采纳全部，刷新页面，确认任务仍存在。
5. 点击任一任务开始学习，确认学习主题、大纲和来源范围对应第三章。
6. 学到最后一节，确认计划项没有自动完成。
7. 返回计划页手动完成，确认只有此时计划状态变为完成。

## 8. 完成定义

V1 完成的标准是：

1. 用户只需在现有对话页说一句计划需求；
2. 现有调度识别 `study_plan` 后，计划真正使用这句话，而非固定推荐；
3. 计划草案可在现有计划页查看、编辑和采纳；
4. 已采纳计划稳定保留教材、章节、知识点范围；
5. 从计划项开始学习时，学习路径严格使用该范围；
6. 直接学习仍然直接学习；
7. 课程完成与计划完成不再互相误判。
